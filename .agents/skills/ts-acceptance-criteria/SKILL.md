# vue-naive-admin TS 改造验收标准（验收 + 测试一体协议）

本项目是 Vue 3.5 + Vite 8 + Naive UI + Pinia 3 + vue-router 5 + UnoCSS 的纯前端后台，已完成 JS→TS 迁移（见 `js-to-ts-migration` skill 与 `docs/ts-migration-progress.md`）。本 skill 定义迁移**之后**的最终验收标准，共四大支柱 + 一套整改规范。

贯穿全协议的改造许可只有一条：**把项目 TS 化**。原 JS 项目的全部功能必须原样保留——不省略、不删除、不简化、不改变任何用户可感知行为（红线 C9，整改细则见 §7）。

1. **支柱 A · 无 JS 痕迹**——仓库里找不出任何"这是 JS 项目改的"的痕迹。
2. **支柱 B · 从零构建标准**——如果这个后台是用 TS 从零开始构建的一个完整项目，它应该达到什么标准，本项目就必须改成什么样。
3. **支柱 C · 代码质量八项 + 功能保留红线**——DRY、可读性、可维护性、可扩展性、可测试性、可复用性、高内聚低耦合、边界条件覆盖；且无论质量多高，原本项目的功能一个不能少。
4. **支柱 D · 测试标准**——测试既是被验收的对象，也是验收的执行手段：单测跑逻辑、类型测试跑契约、冒烟跑应用、功能测试跑业务全流程；方式不限于手动或自动化，但必须让整个项目真正运行起来。

整改规范（§7）约束"按验收结果整改"时的写码行为：不能无脑删除代码，改后质量只升不降。

## 0. 定位与四条铁律

- **验收 + 测试一体，两种模式**：
  - **验收模式（默认）**：只判不改。唯一允许的写操作是保存验收报告（`docs/ts-acceptance-report-YYYYMMDD.md`）；执行测试（单测/类型测试/冒烟/浏览器 GUI 功能驱动）不属于改码。B5 的"类型连通抽测"允许临时改动源文件做编译验证，但必须当场还原并在报告中注明。
  - **整改模式**：仅当用户在同一会话明确说"按验收结果整改"时进入，按 §7 整改规范执行，完成后全量复验。
- **标准不随现状打折**：四大支柱是目标状态，不是对现状的描述。首轮验收出现大量不达标是预期结果——那是发现（findings），不是放宽标准的理由。禁止把"现状如此"写成 pass。
- **功能等价（只许 TS 化）**：验收对象必须保留原 JS 项目的全部功能——不省略、不删除、不简化、不改变任何用户可感知行为；对代码唯一允许做的事是 TS 化（类型化 + 满足支柱 B/C 的等价重构）。红线见 C9，整改细则见 §7。功能回归 = 一票否决。
- **可复现**：每条判定必须附命令输出摘录或 `file:line` 证据；抽样必须用 playbook 固定抽样表；无法机器判定的项标记"需人工复核"，不允许默认 pass。换一个执行者重跑本协议，结论必须一致。

## 1. 验收范围与豁免

- **范围**：整个仓库工作区——src/ 全部、根目录配置（vite/uno/eslint/tsconfig/vitest/package.json/index.html）、`build/` 构建脚本、`src/assets/` 下脚本、tests/（或就近）测试文件、docs/ 文档。
- **豁免**（既不算 JS 痕迹，也不参与手写质量评审）：`node_modules/`、`dist/`、`pnpm-lock.yaml`、自动生成的 `auto-imports.d.ts` 与 `components.d.ts`。
- **项目特有约定**：src/ 中的中文学习注释是本项目的刻意约定，**不是违规项**，不得以"可读性"为由要求删除；只检查注释与代码事实是否一致（陈述错误的要求修正文字）。`docs/ts-migration-progress.md` 是迁移期状态文档，验收时作为 B9 疤痕清单的输入，验收通过后应归档或删除。

## 2. 严重级别与总体判定

- **P0 阻断项**：直接违反四大验收标准的事实性问题——存在 JS 痕迹、strict 未全开、未豁免的显式 any、无测试设施、依赖方向违规、迁移疤痕未闭环、**功能回归**、**测试套件红 / 测试造假（T7）**。
- **P1 必改项**：做到了但质量不达标——覆盖率不足、重复块、超长函数、边界矩阵缺口、命名不一致、测试组织混乱。
- **P2 建议项**：记录，不阻断。
- **总体判定**：存在任一 P0 → **不通过**；0 个 P0 且存在 P1 → **有条件通过**（附整改清单）；0 P0 且 0 P1 → **通过**（P2 仅记录）。
- **基线门槛**：`pnpm typecheck`、`pnpm build`、`pnpm lint:fix` 三绿，且**测试设施已存在时** `pnpm test`、`pnpm test:type` 全绿，是验收前提。基线红 = 记 1 条 P0 并终止后续抽样（先修基线，再重新验收）；测试设施缺失 = T1 一条 P0（不终止扫描，首轮验收继续把问题找全）。

## 4. 支柱 B：从零构建标准（B1–B14）

**总纲**（两条）：

- 把 git 历史遮住，这个仓库读起来必须像一开始就是用 TS 设计的。标准的内容 = "一个用 TS 从零构建的完整后台项目"应有的样子，项目必须改到那个样子，而不是"迁移完成后碰巧的样子"。判别法：对每个可疑点问——"这个文件/这行代码/这条注释会出现在一个从第一天就用 TS 写的项目里吗？"答案为否，即必须改。迁移产物特有的疤痕（妥协断言、保留的 TODO、"行为不变"注释、迁移期遗留文档）从零项目不会有，全部要清。
- 特性是手段，目标是**类型连通**——从 api 响应到页面 render 的整条数据链路上，改错字段名、漏传必填参数、漏处理错误分支，必须在编译期报错。判定标准是"错误用法能否被编译器拦截"，不是"代码里有没有出现类型关键字"。

| # | 条目 | 级别 | 判定方式 |
|---|---|---|---|
| B1 | 编译器强度：`strict` + `noUncheckedIndexedAccess` 开启；`exactOptionalPropertyTypes`、`noImplicitOverride` 有评估结论（开或论证不开，写入报告）。迁移期以"修复成本"为由关闭的必须重新开启并修复 | P0（strict/索引访问）· P1（两项评估） | 读 tsconfig |
| B2 | 显式 any 清零：`as any`、`?: any`、`<any>`、泛型默认 `= any`、`AxiosError<any>` 等全部消灭。确因第三方库类型缺陷无法表达的：行内注释写明缺陷依据 + 报告登记豁免 | 未登记 = P0；已登记但可避免 = P1 | playbook §B 清单命令 |
| B3 | 双重断言 `as unknown as` 同 B2 规则 | 同 B2 | playbook §B |
| B4 | 模板/JSX 内 `as any` 清零：类型不匹配的正规解法是扩展组件类型、泛型组件或修正 props 类型，不是模板断言 | P0 | playbook §B（grep .vue） |
| B5 | 类型连通抽测：抽 3 条端到端链路（playbook §B5 指定），故意写错字段名/漏必填参数/漏错误分支，`vue-tsc` 必须报错。验证后还原 | P0 | 抽测记录写入报告 |
| B6 | 共享类型唯一来源：实体/契约/全局声明集中 `src/types/`；页面级模型可就近定义，但不得跨页复制同形状类型 | P1 | 抽查 + grep 重复形状 |
| B7 | 特性自然存在：类型谓词、可辨识联合+穷举（never 检查）、泛型+约束+默认值、映射类型/keyof typeof、条件类型+infer、模板字面量类型、satisfies、声明合并（RouteMeta/Window）、函数重载、工具类型组合、readonly、unknown 优先——每项在适合它的位置至少一处真实使用；确不适合某特性的，报告说明"为什么不需要"，不许硬塞 | P1 | 对照 module-checklist 的特性落点表 |
| B8 | 类型不说谎：断言只允许用于"比编译器多知道事实"；后端契约妥协（如 `enable: boolean \| 0 \| 1`）必须在 api 边界归一一次，而不是让类型迁就脏形状（除非报告论证归一成本高于收益） | P1 | 抽查断言清单（playbook §B 豁免规则） |
| B9 | 迁移疤痕清零：疤痕关键词（playbook §C）扫描结果逐条定性——要么修复，要么论证为有意设计并改写掉疤痕措辞（"保持原实现/行为不变/迁移妥协/基线老 bug/兼容旧值/遗留/TODO/FIXME"）。`docs/ts-migration-progress.md` 的遗留项清单全部闭环 | P0 | playbook §C grep + 对照遗留清单 |
| B10 | 低效重复与低质量代码清零：**"无调用方"不等于"没有用"**——高质量、可复用的工具/组合函数即使现阶段无调用，也视为后续功能扩展的"预留能力"，保留并在报告登记，不判定违规。必须清除的只有两类：①低效重复（与现有实现重复、或可用明显更少的代码实现同等功能的复制粘贴——收口到唯一实现）；②低质量代码（坏味道/误导性/失效逻辑）。判定流程：knip/grep 找出无调用导出 → **逐个质量定性**（高质量预留 = 保留登记；低效重复 = 收口；低质量 = 删除），报告逐条留痕。**旧数据兼容分支、拼错的持久化键（如 'naivue'）等"看似无用但影响既有用户数据/行为"的代码不得静默删除**——论证保留并去除疤痕措辞（走 B9），或经用户确认后再处理 | P1 | playbook §C + knip（评估清单，非删除清单） |
| B11 | 后端契约单一事实源：实体形状集中在 `src/types/models.ts`，脏形状在 api 边界归一一次，状态/枚举字段字面量联合化 | P1 | 读 models.ts + api 层 |
| B12 | 命名与解法一致性：useXxx/handleXxx/XxxRow/XxxForm 等模式全项目统一；同一问题全项目同一种解法；内部契约必须自洽（如 useCrud 与各页 api 对 id 可选性的约定不得互相矛盾、靠页面断言抹平 = 违规）；props 声明方式统一为类型式 `defineProps<T>()`，不留运行时对象式尾巴 | P1 | 固定抽样表 |
| B13 | 文档反映现状：README 的 TS 说明、docs/ 架构文档与实际结构一致（不得再以 .js 文件名描述现状），命令可照着跑通 | P2 | 核对 |
| B14 | 工具链同标准：vite/uno/eslint/build 全 TS 且类型完整（并入 A1）；tsconfig 是"设计出来的"——分组注释清晰、无注释掉的死配置 | P0（并入 A1）· P2（其余） | 读配置 |

**逐模块核查**：进入本支柱前必读 `references/module-checklist.md`（17 个模块 × 必须体现的特性 × 典型违规快照），按 playbook 固定抽样表逐模块读代码核对。

## 5. 支柱 C：代码质量八项 + 功能保留红线（C1–C9）

**总纲**：八项质量维度 = DRY / 可读性 / 可维护性 / 可扩展性 / 可测试性 / 可复用性 / 高内聚低耦合 / 边界条件覆盖；C9 是红线——质量整改不得以功能为代价。测试的具体标准与执行在支柱 D（T1–T8），C5 与 T1 同源判定。

| # | 维度 | 标准 | 级别 | 判定方式 |
|---|---|---|---|---|
| C1 | DRY | api 层 CRUD 样板工厂化（4 份 api.ts 的 create/read/update/delete 收敛为一个泛型工厂）；页面 CRUD 装配零复制粘贴（差异化只允许经 useCrud 配置）；重复类型组合（`Partial<X> & { pageNo… }`）与跨页重复的行类型/常量/事件处理收口为共享定义；jscpd 扫描无 ≥60 token 的"仅标识符不同"重复块。判定三步法见表下 | P1 | playbook §D(C1) |
| C2 | 可读性 | 函数 ≤60 行（超长须在报告中论证）；文件 ≤400 行（抽检）；无魔法数字/魔法字符串（入字面量联合或具名常量）；命名自解释；注释与代码事实一致 | P1 | 抽样 |
| C3 | 可维护性 | 单一职责；"新增一个资源管理页要动几处"走查达标且模式一致；错误处理策略统一（http 层集中提示，业务层不散落 try/catch 吞错） | P1 | 走查 |
| C4 | 可扩展性 | 新增后端资源/新页面/新布局靠配置、泛型与工厂扩展，不靠复制；MeCrud 列配置可被业务扩展 | P1 | 抽查 |
| C5 | 可测试性 | 代码按可测试性设计：纯逻辑可独立实例化、副作用集中在边界（http/naiveTools/storage）、依赖可注入；测试设施缺失 = P0（与 T1 同源）；用例/覆盖率/类型测试的具体标准与执行见支柱 D | P0 + P1 | playbook §F |
| C6 | 可复用性 | 跨页复用只经 utils/composables/components/api 工厂四条通道；禁止 view→view import；通用结构不得在页面间复制 | P1 | playbook §D grep import 方向 |
| C7 | 高内聚低耦合 | 依赖方向 utils ← composables ← components ← views 违规 = P0；store 不 import 组件/视图；api 层不 import UI；方向规则必须机器化（eslint no-restricted-imports 或等价物，未机器化本身 = P1） | P0/P1 | playbook §D |
| C8 | 边界条件覆盖 | 八类边界矩阵（playbook §D：http 异常族、路由守卫兜底、tab 增删边界、useCrud 并发与空值、storage 损坏数据、MeCrud 空态、表单校验失败路径、404/403）逐格核对，每格"代码有处理 + 有单测佐证" | P1 | 矩阵核对 |
| C9 | 功能保留红线 | 原项目全部功能一项不少、行为不变——不得省略、删除、简化任何功能或交互：按 playbook §E 全功能手测清单逐项核对（执行方式见 T2-L4 与 playbook §F）；整改清单中每个 C1–C8 条目必须标注对应手测点；整改只允许等价重构（只改结构与类型，不改用户可感知行为）。任何功能缺失/省略/行为变化 = P0，总体不通过 | P0 | playbook §E + §F |

**DRY 三步判定法（C1 配套）**——DRY 不是无底线删除重复代码，目标是**用最少的代码实现相同的功能**，只消灭非必要重复：

1. **等价确认**：两段代码行为完全相同才谈合并；"碰巧相似"不是重复。
2. **耦合确认**：收口到唯一实现后，不得把未来会独立演化的逻辑绑死——若收口反而增加耦合，保留重复是正确决策。必要重复白名单：后端契约的镜像形状、有意解耦的相似逻辑、平台/测试的固定样板。
3. **收口方式**：提炼唯一实现（工厂/泛型/组合式函数/共享类型/常量表），"消灭重复"指收敛到一处，不是删代码删到最少行数。

## 6. 支柱 D：测试标准（T1–T8）

**总纲**：测试是验收的执行手段，不只是被检查的对象——支柱 A–C 靠"读 + 扫"，支柱 D 靠"跑"。方式不限定手动或自动化（自动化优先），但必须做到"让整个项目运行起来"：T8 冒烟证明应用能启动，T2-L4 证明业务全流程可用。测试代码本身同样受支柱 B/C 约束（TS 无痕迹、无 any、无重复）。

| # | 条目 | 标准 | 级别 | 判定方式 |
|---|---|---|---|---|

## 7. 整改规范（整改模式专属）

进入条件：用户在同一会话明确说"按验收结果整改"。整改范围 = 报告整改清单，不擅自扩大。细则：

1. **等价重构为默认**：整改的合法动作只有三类——类型化（TS 化）、满足支柱 B/C 的等价结构重构、整改清单列明的缺陷修复。只改结构与类型，不改用户可感知行为（C9）。验收清单中列明的边界缺陷（如空数组崩溃、组件路径匹配失败白屏）允许修复，但必须在整改清单中写明改前/改后行为差异。
2. **禁止无脑删除代码——"无调用"不等于"没有用"**：消灭重复的唯一方式是提炼唯一实现（工厂/泛型/组合式函数/共享类型/常量表）。**高质量的代码即使现阶段无调用方，也视为后续功能扩展的"预留能力"，一律保留**并在整改清单登记。允许删除的只有低效重复与低质量代码，且必须留痕：①低效重复（与现有实现重复、或可用明显更少的代码实现同等功能——附对比证据）；②已被收口的重复（指向唯一实现位置）；③低质量坏味道（附论证）。禁止为"看起来简洁"删除注释、兜底逻辑或功能。对"看似无用但可能影响行为"的代码（旧数据兼容分支、持久化键、防御分支），删除前必须经用户确认，不得以"无调用/死代码"名义静默清除。
3. **改后质量只升不降**：每处整改后的代码必须同时满足支柱 B（类型不说谎、契约自洽）与支柱 C 八项；整改说明须写明"改后比改前好在哪"——对应可读性/可维护性/可扩展性/可测试性/可复用性中的哪一项。
4. **测试同步**：被改动逻辑的既有测试同步更新（T7）；新增或重构的纯逻辑补充 L1 单测与必要的 L2 类型测试；整改完成后 `pnpm test` / `pnpm test:type` 必须全绿。
5. **小步前进**：每完成一个整改条目 → `typecheck`/`build`/`lint`/`test` 全绿 → 对应 §E 验证手测点实测通过 → 再进下一条。
6. **不顺手改需求**：不新增功能、不改交互与文案；过程中发现清单外的新问题，先登记再定，不擅自处理。
7. **全量复验收口**：整改完成后重跑本协议全部流程（含支柱 D 与 C9 功能等价核对），产出新报告；旧报告保留作对照。

## 8. 执行流程（每次验收按此顺序）

1. **准备**：读本 skill 全文 + `references/audit-playbook.md`；确定报告文件名 `docs/ts-acceptance-report-YYYYMMDD.md`。
2. **基线**：`pnpm typecheck && pnpm build && pnpm lint:fix` 三绿；测试设施已存在时 `pnpm test`、`pnpm test:type` 全绿。基线红 → 记 P0，终止；测试设施缺失 → 记 T1 P0，继续把问题找全。
3. **机器扫描一轮拿全证据**：A1–A7（§A）、B2–B4 断言清单（§B）、B9 疤痕与 B10 低质/冗余评估（§C）、C1 重复扫描与 C6/C7 耦合方向（§D）——playbook 命令一次跑完，输出登记。
4. **支柱 B 逐模块**：读 `references/module-checklist.md`，按固定抽样表读代码，执行 B5 类型连通抽测（临时改动 → vue-tsc 报错 → 还原）。
5. **人工项**：B9 疤痕逐条定性、B10 无调用导出逐个质量定性（高质量预留 = 保留登记；低效重复 = 收口；低质量 = 删除）、B11 契约核对、B12 一致性抽样、C8 边界矩阵代码侧核对。
6. **测试执行（支柱 D）**：跑 `pnpm test` / `pnpm test:cov` / `pnpm test:type`，核对 T1 设施、T3 组织、T4 编写规范抽读、T7 诚信扫描、T8 应用冒烟（playbook §F）。
7. **功能等价核对（C9）**：按 §E 清单执行——方式 A 浏览器 GUI 自动化优先，方式 B 人工；结果逐项登记（playbook §F 执行协议）。
8. **汇总写报告**：每条目 pass / fail / 需人工复核 + 严重级别 + 证据；模板见 playbook §报告模板。
9. **总体判定 + 整改清单**：按 P0→P1 排序，每条含证据、一句话建议方案、对应 §E 手测点；整改模式的入口与行为准则见 §7。

## 9. 自校准

`references/audit-playbook.md` §H 记录了 2026-10-04 快照下首轮验收必须能重新发现的证据集合（8 个 .js、约 30 处 any、零测试设施、无功能层自动化、17 个无调用导出、两处运行时式 props 声明等）。执行扫描后先对照它：**如果这些证据一个都没扫出来，说明扫描命令没跑对，先修扫描再谈判定**。该清单会随后续整改失效，每次验收后应更新时间戳与内容。
